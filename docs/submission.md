# 源码内历史提交说明

**本文件和 `scripts/build_submission.py`、`scripts/verify_package.py` 是保留在源码中的
历史开发入口，不适用于本次比赛提交包。**

本次材料以顶层目录 `00_提交说明/` 为准，必交 PPT 位于 `01_必交材料/项目介绍/`。
本包带 `frontend/dist` 预构建界面，普通启动不需要再构建前端。外层 ZIP 采用
“公司/团队名+作品名”的同名顶层目录，而旧源码校验脚本要求源码直接位于 ZIP 根目录，
并拒绝 `dist`；不要用旧脚本核验或重打包当前材料。

旧文档和生成脚本中的具体日期、冲刺安排及旧 ZIP/PPT 名称均未核实为本次赛事要求，
不得据此判断实际截止日期。提交期限以实际官方平台或组委会确认为准。
下面的历史内容仅用于理解旧开发流程，不作为当前提交指引。

## 必交 PPT

运行 `scripts/build_submission.py` 后生成 `artifacts/submission/SparkGuard-初赛项目介绍-草稿.pptx`。内容涵盖团队介绍、背景、功能、技术架构、模型作用、实际测量、安全边界、原创性声明草稿与后续验证。团队资料未提供，不能替你编写履历和合作方；没有签署声明。

PPT 中全部测量由 `artifacts/benchmark*.json` 读取，历史模型截图来自先前浏览器验证，PPT 明确标记为历史界面；当前 React 截图与报告位于 `artifacts/ui-react/`。草稿不应未经审核直接提交。

## 3–5 分钟真机视频脚本

1. 0:00–0:30：展示设备与真实摄像头，说明已有质检告警增加时需区分成像问题与产品问题。
2. 0:30–1:00：采集正常基线，展示数据源和官方模型 SHA、服务进程与 GPU 运行记录。
3. 1:00–2:00：真实制造失焦 / 光源变化，观察指标与规则报警；软件扰动演示必须显式注明。
4. 2:00–3:00：输入真实维护记录，请求 Spark 复核；展示原始输出、竞争原因和人工验证，不隐藏误判。
5. 3:00–4:00：恢复条件，观察指标回归；演示历史与 JSON 下载。
6. 4:00–4:30：关闭网络后再调用模型，说明仅供人工决策，无自动产线控制。

开发环境的自动化录屏不等于可提交的真机摄像头演示。历史 Windows 摄像头曾能读帧，但低信号取景已被拒绝校准，需检查遮挡、曝光并摆放可检验样品后再录制。

## 对照与消融

冻结采集集、提示词和模型版本，避免选择有利样例：

- 规则观测 vs Spark 复核，保持相同输入。
- Spark 无操作员记录 vs 有操作员记录。
- 1.7B vs 4B（同一量化与上下文范围）。
- 如需“替换不可轻易成立”的证据，再对照一个可部署的同档模型。

报告类别判定、数字忠实度、备选原因、可执行验证步骤、错误建议和成本。根因与产品真缺陷须人工标注；合成故障标签不可作为模型输入。模型类别错误仍是错误，即使输出流畅。

## 提交 ZIP

打包脚本只收集源代码、配置、复现文档、模型来源清单、PPT与精选证据；包含 `frontend/` 源码、配置与 npm 锁文件，解包后须执行 `npm ci --prefix frontend` 和 `npm run build --prefix frontend`。不包含 `node_modules`、`frontend/dist`、`.venv`、Ollama缓存、大模型权重、SQLite实时库和个人系统日志。完成团队资料后，名称自动按“团队名+作品名”生成。

模型超过1GB，本 ZIP 采用官方固定仓库下载脚本复现。如组委会要求安装包离线附带权重，需另提供合法权重与永久有效云盘链接，并复核总包大小与模型许可。

## 隔离包复现

`scripts/verify_package.py` 校验 ZIP 与当前源码字节一致性，再解包到独立目录，安装 Python / npm 锁定依赖、构建 React 并执行后端测试。支持 Windows 与 macOS / Linux；默认仅使用缓存，缺少依赖会失败，可显式传 `--online` 下载。缓存位置通过 `--cache-dir` 和 `--npm-cache` 指定。此验证不包含浏览器、模型、摄像头或第二台设备。

```sh
python scripts/verify_package.py --cache-dir .uv-cache --npm-cache .cache/npm --online
```

生成提交材料前审阅目标路径；验证 ZIP 时可传 `--zip <文件>`，无需预先存在 build-report。
